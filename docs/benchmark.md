## 成本：这本书到底花了多少

实测 tokens：**521,124 输入 / 146,398 输出**。按不同计费方式换算同一本书：

| 计费方式 | 这本书 | 说明 |
|---|---|---|
| 本次实际（`Qwen/Qwen2.5-7B-Instruct`） | **¥0** | 定价页标注 Free，输入输出都是 0/0 |
| 按 `Qwen2.5-14B` 价（输入 0 / 输出 ¥0.35/M） | ≈ ¥0.05 | 半免费模型 |
| 按 `GLM-5.3-Flash`（¥0.8 / ¥2.8 每百万） | ≈ ¥0.83 | |
| 按 GPT-4o-mini（$0.15 / $0.60 每百万） | ≈ ¥1.2 | 汇率按 7 估 |
| 按 Google Translate API（$20 / 百万字符） | ≈ ¥58 | 按 40 万英文字符粗估 |
| 人工翻译（¥80–200/千字） | ¥8,000+ | 按 10 万汉字估 |

结论：**即使全部换成付费小模型，一本也就一块钱上下**。
真正贵的是按字符计费的传统机翻 API，不是 LLM token。

内存这一点值得单独说：1.7 GB 的机器上跑满整本书只用了 44.6–52 MB
（本机 psutil 与服务器 `ru_maxrss` 口径不同），`MemoryMax=320M` 有 6 倍以上余量。原因是逐章解析、译文只落 SQLite、最后才组装 zip，
峰值只跟「一章的大小」有关，与全书无关。

真实 API 运行时额外开销主要是 HTTP 响应缓冲（单个响应通常 < 20 KB），
按 60–100 MB 估算是安全的。

### 8 个待复核段的原因（全部保留原文，不产出坏结构）

| 原因 | 数量 | 典型场景 |
|---|---|---|
| 译文过短（比例 < 0.15） | 2 | 模型偶发返回极短输出，重试与降级后仍不合格 |

### 已知质量问题

- `fantasy` 在译文里同时出现「幻想」和「奇幻」。术语表抓到了 48 个专名，
  但没把核心概念词 `fantasy` 收进去。**这是设计选择**：概念词靠人工在面板里加一条
  `fantasy => 奇幻`，之后重跑只重译命中段，比让模型自己猜更可靠。

```bash
# 或者跑单次 CLI 时：
/usr/bin/time -v slowtrans run --src book.epub --out out.epub
```

## 走过的弯路（都是真实踩出来的）

1. **行首占位符最容易被丢**：`{{0}}Thanks...` 里的小模型经常把 `{{0}}` 当没用的符号删掉。
   → 改成「首尾占位符物理剥离，不发模型」，成功率从 ~85% 提到 100%。
2. **在段内加 `（本段必须保留：{{0}}）` 提示会污染译文**：翻译专用模型会把括号内容一起译出来。
   → 提示只放 system prompt，段内保持干净。
3. **固定「一次 4 段」会炸**：四个长段叠起来 prompt 上万字符，免费模型直接 60 s 超时。
   → 改成按总字符数（2600）动态分批。
4. **`<blockquote><p>` 会重复计数**：块级元素必须只看"叶子块"。
5. **纯图片块会产生大量"空译文"复核**：摊平后没有文字的分段直接不入库。
6. **`INSERT OR REPLACE` 会把 `seg_done` 清零**：改 UPSERT 并只更新元数据。
7. **`--limit` 截断过的章续跑会缺尾段**：`INSERT OR IGNORE` 是幂等的，每章都该重扫。
8. **`<span>` 包着的标题整段漏译**：早期把 span/em/strong 全部当占位符保留，
   结果 `<h1><span class="chaptertitle">Title</span></h1>` 的文字从没进翻译队列，
   纯中文版开头还是英文。修正后内容型内联元素展开取文本，只有空锚点/图片/上标保留。
   代价：已有任务有 1033 段模板变化被重置重译（一次性）。
9. **分段规则改了但老段不更新**：主键是 (章,块,段)，`INSERT OR IGNORE` 会静默跳过，
   修正永远不生效。现在显式比对 `src_text`，变了就重置成 pending。
