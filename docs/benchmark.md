## 免费模型对比（同一批 4 段正文，约 3500 字符）

| 模型 | 服务商 | 耗时 | 4 段全部返回 | 备注 |
|---|---|---|---|---|
| `THUDM/GLM-4-9B-0414` | 硅基流动 | 11.0 s | 是 | 短文本最快；长 prompt 时偶发 60 s 超时 |
| `Qwen/Qwen2.5-7B-Instruct` | 硅基流动 | 11.7 s（3 段） | 是 | 中文最自然，最终选用 |
| `tencent/Hunyuan-MT-7B` | 硅基流动 | 18.9 s | 是 | 纯翻译模型，会把指令文本一起翻译，不适合带 prompt 的流程 |
| `glm-4-flash` | 智谱 | 25.6 s | 是 | 独立配额，作为备用通道 |

> 免费额度/模型名随时会变。上表是 2026-10 的一次性测量，不是基准承诺。
> 真正的结论是：**免费模型对长 prompt 的响应时间在 8–25 s 量级，必须按字符数动态分批**。

## 走过的弯路（都是真实踩出来的）

1. **行首占位符最容易被丢**：`{{0}}Thanks...` 里的小模型经常把 `{{0}}` 当没用的符号删掉。
   → 改成「首尾占位符物理剥离，不发模型」，成功率从 ~85% 提到 100%。
2. **在段内加 `（本段必须保留：{{0}}）` 提示会污染译文**：翻译专用模型会把括号内容一起译出来。
   → 提示只放 system prompt，段内保持干净。
3. **固定「一次 4 段」会炸**：四个长段叠起来 prompt 上万字符，免费模型直接 60 s 超时。
   → 改成按总字符数（2600）动态分批。
4. **`<blockquote><p>` 会重复计数**：块级元素必须只看"叶子块"。
5. **纯图片块会产生大量"空译文"复核**：摊平后没有文字的分段直接不入库。
6. **`INSERT OR REPLACE` 会把 `seg_done` 清零**：改 UPSERT 并只更新元数据。
7. **`--limit` 截断过的章续跑会缺尾段**：`INSERT OR IGNORE` 是幂等的，每章都该重扫。
